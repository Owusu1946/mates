# Share to a mate: backend handoff for Ken

## Context

The mobile branch has the iOS share target, App Group cache, Clerk credential bridge, SwiftUI picker, direct upload/run flow, and pending-share retry screen. A local Expo prebuild and simulator build compiled the extension for iPhone 16 Pro. On that simulator, URL, a small PDF, and a PNG photo were shared to Kwame; each appeared in chat with an assistant response, and existing visible turns stayed in the conversation. Safari required the extension activation predicate to account for file UTIs and extra provider representations; that fix is included in the current mobile diff. A forced upload/run failure and a retry have not yet been verified. The desired flow is: share a URL, image, or PDF from another app, choose a mate (last used preselected), add an optional note, send, and have the resulting user message and run appear in that mate's chat with the existing push path.

The config plugin now scopes the build file to the share extension's frameworks phase. After that change, a clean iOS prebuild, CocoaPods installation, and simulator build succeeded; ClerkKit is present in the extension's package dependencies and frameworks phase.

The mobile plan and progress are in [`share-sheet-plan.md`](./share-sheet-plan.md). First-release scope is one item per share; voice notes are deferred. No audio API work is requested for this release.

## Existing backend behavior to build on

Post-audit mobile fixes (uncommitted): after Android sign-in, the root route reopens a live inbound share intent; a second share arriving over an existing pending draft is explicitly rejected and the user is told to share it again. The iOS extension marks a saved share as sending, then failed on error; Mates offers retry only after failure or ten minutes without a completion signal. A signed-out Android share remains in expo-sharing's process memory during sign-in; preserving it across process termination still needs a separate durable pre-auth staging flow if that becomes a release requirement. These changes need native device checks.

- `POST /v1/attachments` accepts an authenticated multipart file, stores it for the user, returns its attachment metadata, and enforces a **4 MiB per-file** limit.
- `POST /v1/runs` accepts `chatId`, `requestKey`, `assistantMessageId`, `parentId`, and `messages`. A user message can include attachment IDs. The API validates ownership, links the attachments to the chat, and submits the durable run.
- **History branch root cause and mobile fix:** iOS previously submitted a new `parentId` (`user_share_<uuid>`) without first saving that user message into the chat history. `submitRun()` inserts a missing row without a `parentId`, making it a new root; the assistant reply hangs from it. Mobile `recentBranch()` follows the newest leaf, hiding earlier messages from view although their rows remain stored. The mobile fix now reads `GET /v1/chats/:id/messages`, selects the newest leaf using the same graph rule as `recentBranch()`, and saves the share user message through the existing `PUT /v1/chats/:id/messages` contract before `POST /v1/runs`. It saves attachment display metadata in that same message. No new API route or deployment is expected.
- **Development history repair (optional):** the new mobile pre-save prevents future sends from introducing another disconnected root. It does not reconnect root share messages already stored by earlier builds. If the older development chat needs restoration, review a safe one-time history repair (or an API history normalization) that links each orphaned `user_share_` root after the preceding chat leaf, preserving chronological order and any intentional branches. Test that reopening the affected chat restores its earlier messages.
- **Verification status:** URL, small PDF, and photo shares were sent to Kwame from Safari on the iPhone 16 Pro simulator. Earlier visible chat turns remained visible; each attachment showed in chat and received an assistant response. A 4.2 MB PDF was rejected with the expected 4 MB message. This verifies API authorization and the existing attachment/run contract for those types. No new API route or schema was needed. A simulator history branch already lacked messages from before an earlier share, so this fix does not restore older orphaned roots.
- **Remaining review:** Ken may review recovery for orphaned `user_share_` roots from earlier development builds. This is an optional repair of earlier development data, not a release deployment requirement. Confirm a run retry reuses the same message ID, upload ID, and run idempotency key.
- Run completion already uses follow-up processing and the existing push delivery mechanism. Preserve this path; no new push provider or share-specific endpoint is currently justified.
- The typed API contract lives in the shared contract package and must stay aligned if backend behavior/schema changes.
- No API or backend deployment change is currently indicated for links, photos, or PDFs. The app can send those through the existing upload/run routes. Android implementation does not introduce an API contract change.

## Ken's backend scope

1. **No audio behavior is in the first-release scope.** Do not add audio/video upload or transcription support unless mobile reopens that scope.
2. **Preserve retry and push behavior.** Run submissions are idempotent by `requestKey`, but attachment uploads are not. The mobile flow uploads before creating a run, so determine whether unlinked attachments need cleanup or whether retry can safely retain/reuse an upload. Verify share-originated runs trigger the existing push follow-up and keep `chatId` in notification data.
3. **Keep API changes narrow and backward compatible.** Add contract changes only when request/response behavior changes. No API change is currently indicated for one URL, image, or PDF per share.
4. **Own API deployment only if a concrete backend change is needed.** Document required environment/configuration changes, deploy before a dependent native app release, and report the deployed version/commit plus a smoke-check result to mobile. Do not put server credentials in `apps/mobile` or the iOS App Group.

The iOS extension credential design is a mobile/native concern. Do not add a `/v1/token` or similar exchange endpoint as a shortcut; Clerk's session token is a short-lived JWT, and any long-lived credential exchange needs an explicit reviewed authorization model.

## Not currently requested

- No new share-specific API route unless a concrete contract issue is found.
- No new push delivery service; reuse existing run follow-ups.
- No database migration unless audio processing requires persisted transcript/status metadata beyond the existing attachment fields.
